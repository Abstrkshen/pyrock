Compile ordinary Python into a native program, through Rust you can read.

pyrock works out the types of unannotated Python from how each function is called, writes one Rust function per combination of types, and builds the result with Cargo. Code it can't compile keeps running in an embedded CPython, and pyrock lists every line where that happens.

How it works

A program goes down through six layers, from the Python you wrote to machine code. Here is fib at each of them.

1

Python source

Plain Python: no annotations, no decorators, no special syntax. Imports next to the file can be .py, .rs or .c.

def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

print(fib(30))
2

CPython's parser

pyrock asks your own python3 for the syntax tree, so parsing matches the language exactly, then resolves names and imports into its own IR.

crates/frontend

{"_t": "FunctionDef", "name": "fib", ...
 "body": [{"_t": "Return", "value": {"_t": "IfExp",
   "test": {"_t": "Compare", "ops": [{"_t": "Lt"}], ...
3

Generic signatures

Each function gets a signature with constraints instead of types: fib works for any A that supports <, - and + the way it uses them.

crates/infer

fib(A) -> A where Lt(A, int), Sub(A, int, A), Add(A, A, A)
4

Specialization

Starting from the module body, pyrock follows the actual calls with concrete types until nothing changes, then decides for each piece: native, or through CPython.

crates/infer, crates/analysis

fib(n: int) -> int   native  fib__int
    effects: may_raise  recursive
Runtime: no CPython needed
5

Rust

One Rust function per specialization, with Python's semantics kept: checked integer overflow, the recursion limit, exceptions as Result.

crates/codegen-rust, crates/runtime

fn fib__int(mut n: i64) -> PyResult<i64> {
    let _frame = rt::enter()?;
    return Ok((if (n < 2_i64) { n } else {
        rt::int::add(fib__int(rt::int::sub(n, 1_i64)?)?,
                     fib__int(rt::int::sub(n, 2_i64)?)?)? }));
}
6

A native executable

Cargo and rustc do the rest. A program with no boundaries doesn't link libpython at all; one with boundaries embeds CPython for exactly those lines.

crates/driver

$ pyrock run fib.py --release

$ ls .pyrock/fib/

Correctness is checked by running every test program under both CPython and pyrock and comparing standard output, exit status and the final exception line. Details: docs/how-it-works.md.

Install

pyrock is a single binary. It writes Rust and builds it with Cargo, so your machine also needs a Rust toolchain.

Install script

Downloads the right binary from the releases, checks its SHA-256 and puts it in ~/.local/bin.

curl -fsSL https://raw.githubusercontent.com/\
Abstrkshen/pyrock/main/install.sh | sh
pyrock --version

PYROCK_INSTALL_DIR changes the folder, PYROCK_VERSION=v0.1.0 picks a release.

Release archive

Download pyrock-<target>.tar.gz from the latest release, compare it with SHA256SUMS, and put pyrock on your PATH.

Targets: x86_64-unknown-linux-musl, aarch64-unknown-linux-musl (static, any distribution) and aarch64-apple-darwin.

From source

Any platform with Rust. The binary carries its runtime, so the clone isn't needed afterwards.

cargo install --git \
  https://github.com/Abstrkshen/pyrock pyrock

What else it needs

  • Rust, from rustup.rs (tested with 1.96). The first build of any program compiles the runtime into ~/.cache/pyrock/target in a minute or two; later builds take seconds.
  • Python 3 (tested with 3.12). pyrock parses with it, and programs that use Python packages embed it, which needs the shared libpython (on Debian and Ubuntu: sudo apt install python3-dev).
  • A C compiler, only if your programs import .c files.

Usage

Point pyrock at your program's entry file. Everything it imports from the same folder is compiled into one executable.

  1. pyrock check main.py

    Reports what won't compile, each problem with a code, a line and a reason. Builds nothing, so it's quick.

  2. pyrock explain main.py

    Shows how imports resolved, the types inferred for each function, and every line that goes through CPython.

  3. pyrock run main.py

    Builds and runs. Arguments after -- go to your program. Output and exit status match python3.

  4. pyrock bench main.py

    Times a --release build against CPython and checks that both print the same thing.

Hybrid mode, the default

Anything pyrock can't compile natively runs in an embedded CPython: imported packages such as json, numpy or langchain, and values that don't have a single type.

  • Every such line is a reported boundary, listed by explain.
  • Native functions and objects can be passed to Python and called back.
  • The executable needs the Python it was built with.

--mode native-only

Every boundary becomes a compile error, so what you get is pure Rust.

  • The executable doesn't link libpython and runs without Python installed.
  • Rust and C files are still imported natively.
  • Use pyrock check --mode native-only to keep a program that way.

Where it helps

Loops over numbers, strings, lists, dicts and your own classes: simulation, game logic, parsers, tokenizers, request handling. These become plain Rust with no object boxing and no interpreter.

Where it doesn't

Code that spends its time inside Python packages (numpy, OpenCV, an HTTP framework) runs at the same speed, because that work still happens in CPython. Each crossing into CPython costs about 15 ns, so keep hot loops on native values.

What pyrock does differently

  • No annotations needed: types come from the calls, and one function can become several specialized ones.
  • You can read what it produced. The Rust has a comment on every function pointing at its Python line, and explain lists every decision.
  • The boundary with CPython is explicit, per line, and can be turned into errors.
  • import stats loads stats.rs or stats.c directly. No bindings, no build files.

What to know before you try it

  • It's a prototype, developed and tested on Linux.
  • Integers are 64-bit: results beyond that raise OverflowError where CPython would grow the number.
  • Compiling needs Rust, and a first build takes a minute or two.
  • Tracebacks show only the final line, and some Python (match, metaclasses, classes based on dict or pydantic) isn't supported yet.

Roadmap

The goal is to compile enough of the Python that backend, AI and GUI apps actually use, and to make existing C and Rust code easy to call. Each step is logged with how it was verified in docs/roadmap.md.

Done

  1. Phase 1: types and everyday syntaxParametric types, exceptions, with, defaults and keywords, Optional, module globals.
  2. Phase 2: native collectionsLists, dicts, sets and tuples with CPython's aliasing, comprehensions, unpacking, formatting.
  3. Phase 3: classesMethods, properties, dataclasses, inheritance, user exceptions, polymorphism.
  4. Phase 4: closures and callbacksLambdas, nested functions, decorators, native functions callable from Python.
  5. Phase 5: Rust and C interopSlices, buffers, structs, handles with methods, callbacks, Cargo dependencies.
  6. Phase 6: async and generatorsasync/await on asyncio, generators, async generators, finalization.
  7. Phase 7: faster mixed codeA cheaper CPython bridge, threads, record dicts as structs, native math.

Phase 8, in progress

  • Packages, relative imports, imports inside functions
  • Enums, ABCs, dataclass options, NamedTuple, multiple inheritance
  • Protocol, Generic, TypedDict, cached_property
  • match statements
  • Arbitrary-precision integers
  • Classes based on CPython classes (dict, pydantic.BaseModel)
  • Full tracebacks through the source map
  • Releasing the GIL during long native computations
  • macOS in CI, and benchmarks of compile time, memory and binary size

How much of Python compiles today

52 of Python 3.12's 55 statement and expression kinds. Measured on code as it is, 64% of the standard library's functions and methods are accepted, and 83%, 75% and 50% of those in requests, huggingface_hub and langchain_core. See docs/coverage.md and the supported subset.
